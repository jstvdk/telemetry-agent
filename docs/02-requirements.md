# 02 · Requirements and use cases

## Users

| Persona | Context | Needs |
|---|---|---|
| **Shift operator** | Night shift, several subsystems, sometimes several cameras | Know fast whether something is wrong and why; a shift log without hand-writing it |
| **Camera expert (on call)** | Woken up for escalations | A precise summary: timeline, evidence, what was already checked |
| **Instrument scientist** | Next morning | What happened overnight, how much data was lost, any recurring faults |

## Use cases

| ID | Use case | Mode | Example |
|---|---|---|---|
| **UC-01** | Explain a failure | Agent | "Why did the readout restart at 02:13?" → cause hypothesis citing the config change event and runbook entry |
| **UC-02** | Situation summary | Agent | "Anything wrong in the last hour?" → list of active issues with severity and event IDs, or "nominal" |
| **UC-03** | Trend check | Agent | "Is any temperature drifting?" → channel, slope, window, compared with baseline |
| **UC-04** | Factual lookup | Agent | "How many HV trips tonight?" → exact number from the timeline |
| **UC-05** | Shift log draft | Pipeline | End of shift → markdown log: timeline, incidents, open issues, each line linked to events |
| **UC-06** | Decline gracefully | Agent | "What was the sky brightness?" (no such data) → "not available in the monitored sources" |
| **UC-07** | New error signature | Pipeline | An error template never seen before → flagged event; later a question to the team channel |

UC-01 is the core value (Stage 0 in [00](00-journey.md)). UC-05 is the fallback value: it is useful even if the agent is not.

## Functional requirements

| ID | Requirement | Use cases | Status |
|---|---|---|---|
| FR-01 | Ingest log messages and telemetry from a stream; keep **source** timestamp (UTC), camera, subsystem, level as separate fields | all | 🔨 v0 stores ingest time and raw text only |
| FR-02 | Detect limit violations, rate-of-change trends, heartbeat gaps, process restarts, config changes, tracebacks and new error signatures as **events with stable IDs** | 01–05, 07 | 📐 |
| FR-03 | Store events in one queryable timeline | 01–05 | 📐 |
| FR-04 | Expose read-only tools: `query_timeline`, `get_event`, `get_telemetry_features`, `search_runbook` | 01–04, 06 | 🔨 v0 has raw-text tools |
| FR-05 | Same tools available over MCP and to the built-in agent, from one definition | — | 🔨 v0 has three copies |
| FR-06 | Agent returns a **structured final answer**: text, claims, citations, status (`answered` / `insufficient_data` / `out_of_scope`) | 01–04, 06 | 📐 |
| FR-07 | Validator checks each citation exists and each cited value matches the evidence; flags `ai-draft` runbook citations | 01–05 | 📐 |
| FR-08 | Shift-log pipeline produces markdown with event links | 05 | 📐 |
| FR-09 | Log per call: model, tokens (incl. cache), latency, tool calls, errors | — | 🔨 v0 logs tokens only |
| FR-10 | Simulator generates scenarios with ground-truth labels, reproducible from a seed | eval | 📐 |

## Non-functional requirements

| ID | Requirement | How it is checked |
|---|---|---|
| NFR-01 | **Read-only.** No tool can modify any system; tools open the DB read-only | T-SAFE-01, T-SAFE-02 |
| NFR-02 | **Fail-silent.** Assistant failure never affects collection or detection | Detection runs without the LLM layer; T-E2E-02 |
| NFR-03 | **Reproducible.** Same snapshot + same scenario seed → same tool outputs | Relative "now" = newest record; T-TL-01 |
| NFR-04 | **Model-agnostic.** Swap model by config; runs on a local open-weight model | T-AG-06, experiment E2 |
| NFR-05 | **Bounded cost.** Tool output caps; max steps; token usage reported per question | Eval report |
| NFR-06 | **Latency.** UC-01–04 answered in < 30 s p95 on a hosted model (target, to measure) | Eval report |
| NFR-07 | **Runs anywhere.** `make demo` on a laptop with no external services except an LLM endpoint | T-E2E-01 in CI with a fake model |

## Out of scope (v1)

- Any action: commands, restarts, config changes, code changes.
- Telescope structure, weather, scheduling and transient alerts.
- Any role in the safety chain.
- A new UI. Output is markdown, CLI and MCP.

## Acceptance criteria for the v1 demo

The vertical slice is "done" when, on the synthetic scenario set:
1. every injected fault produces the expected detection event (detection recall = 1.0 on the scripted set);
2. the nominal scenario produces **zero** alerts;
3. after validation, **no** answer contains an unflagged citation to something that does not exist;
4. the eval report is generated by one command and includes accuracy, grounding, tokens, cost and latency per model;
5. the full pipeline runs in CI with a fake model (no API key needed).

Answer-accuracy targets are set *after* the first baseline run (see [04](04-evaluation.md)), not guessed in advance.
